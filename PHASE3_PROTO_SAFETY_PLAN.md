# Phase 3: Proto Safety — Detailed Implementation Plan

*Generated: 2026-05-20*

## Objective

Replace all `GetXxx()` method calls on protobuf messages with direct field access using nil-safe helper functions. The `GetXxx()` methods generated by protobuf hide nil pointer dereferences by returning zero values, but they make code harder to audit for nil safety and violate the project's coding standards (see AGENTS.md: "NO GetXxx() method calls on proto messages").

## Scope

- **client/ directory**: ~122 `GetXxx()` calls across 5 files
- **pkg/ directory**: ~1098 `GetXxx()` calls across multiple files
- **Total**: ~1220 instances

## Strategy

### Categories of GetXxx() Calls

1. **Scalar field access** (e.g., `GetPrice()`, `GetVolume()`, `GetName()`) — Replace with `getXxx()` helper or direct `*field` with nil guard
2. **Message field access** (e.g., `GetS2C()`, `GetBasic()`, `GetSecurity()`) — Replace with nil check + direct field access
3. **RetType/RetMsg pattern** (e.g., `rsp.GetRetType()`, `rsp.GetRetMsg()`) — These are on the top-level response and are always safe (proto response is never nil after successful send). Replace with direct `rsp.RetType` / `rsp.RetMsg`
4. **Repeated field access** (e.g., `GetAccList()`, `GetOrderList()`) — These return nil-safe slices. Replace with direct field access + nil guard on iteration
5. **Nested chain access** (e.g., `s.GetBasic().GetSecurity()`) — Most dangerous. Must add nil checks at each level

### Helper Functions

The `client/` package already has these helpers (`client/client.go:299-338`):
- `getStr(s *string) string`
- `getInt32(i *int32) int32`
- `getBool(b *bool) bool`
- `getFloat64(f *float64) float64`
- `getInt64(i *int64) int64`
- `getUint64(i *uint64) uint64`

The `pkg/` package needs the same helpers added to a shared utility file.

### Replacement Rules

| Pattern | Replace With | Notes |
|---------|-------------|-------|
| `obj.GetPrice()` | `getFloat64(obj.Price)` | Scalar float64 field |
| `obj.GetName()` | `getStr(obj.Name)` | Scalar string field |
| `obj.GetVolume()` | `getInt64(obj.Volume)` | Scalar int64 field |
| `obj.GetRetType()` | `obj.RetType` | Top-level response field, always safe |
| `obj.GetRetMsg()` | `obj.RetMsg` | Top-level response field, always safe |
| `obj.GetS2C()` | nil check + `obj.S2C` | Must check S2C != nil |
| `obj.GetAccList()` | `obj.AccList` | Repeated field, nil-safe for range |
| `s.GetBasic().GetSecurity()` | nested nil check | Must check s.Basic != nil first |
| `d.GetCode()` where d is *Security | `getStr(d.Code)` | If d itself is already nil-checked |

2. Process `client/` files (Batch 1) — 5 files
3. Process `pkg/` files (Batch 2) — ~10 files
4. Run `go build ./... && go vet ./... && go test -race ./...` after each batch
5. Update CHANGELOG.md and IMPLEMENTATION_PLAN.md

## Safety Rules

- **NEVER** change proto-generated files (`pkg/pb/`)
- **ALWAYS** run build+vet+test after each file modification
- **ALWAYS** add nil checks when replacing chained GetXxx() calls like `a.GetB().GetC()`
- For `RetType`/`RetMsg` on top-level response: direct access is safe (response is never nil after successful proto.Unmarshal)
- For `S2C` access: MUST check `S2C != nil` before accessing fields
- For repeated fields: direct access is safe for `range` (nil slice ranges to zero iterations)
